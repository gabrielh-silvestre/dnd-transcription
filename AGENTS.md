# OMX v2 AGENTS

You are working inside a repo that uses oh-my-codex v2.

## Default operating model

- Start from `$ultrawork` unless the user explicitly asks for a narrower workflow.
- Route unclear or risky work through `$deep-interview`.
- Turn broad work into durable slices with `$plan`.
- Escalate to `$team` only when parallel durable execution is worth the overhead.
- Keep `.omx/` honest. If the HUD says a mode is active, there should be artifacts or tasks proving it.

## Durable artifacts

Maintain these when relevant:

- `.omx/plans/*.md`
- `.omx/research/*.md`
- `.omx/logs/execution-ledger.md`
- `.omx/memory/*.json`
- `.omx/state/*-state.json`
- `.omx/state/tasks.json`
- `.omx/state/reviews.json`
- `.omx/state/inbox.json`
- `.omx/team/team.json`

## Agent roles

- `architect`: boundaries, risks, sequencing
- `planner`: execution slices, requirements, verification map
- `researcher`: brownfield map, research summary, open questions
- `executor`: one scoped slice, one explicit verify handoff
- `reviewer`: findings first, coverage gaps, residual risk
- `operator`: queue health, worker health, inbox clarity

## Team runtime rules

- Worker ids must map to real catalog roles.
- Task claims must map to a real worker.
- Every completion should generate a reviewable handoff.
- Every review should end in `approved`, `changes_requested`, or stay `pending` for a clear reason.
- Use inbox messages for next actions, not narration.

## Plugin and hook rules

- Prefer the first-party OMX plugin bundle when testing plugin flows.
- Treat Codex hooks as experimental. Install them when useful, but keep degraded behavior correct when `codex_hooks` is off.
- Repo-local hook installs belong in `<repo>/.codex/hooks.json`.
- Personal hook installs belong in `~/.codex/hooks.json`.

## Product boundary

OMX v2 is Codex-native. Do not reintroduce `claude_code*` tools or the old Codex-to-Claude split unless the repo owner explicitly chooses to build an adapter later.

## Project commands

- `npm run build` compiles TypeScript to `dist/` and clears stale artifacts before `tsc`
- `npm test` runs the build plus the full Jest suite on `dist/tests`
- `npm run transcribe -- --input <file> --output <dir> --provider <fake|openai-whisper|openai-transcription>` runs the real transcription CLI
- `npm run wiki -- <init|refresh|ingest|query|lint>` maintains the repo-local code wiki in `docs/wiki/`

## Shared project memory

- Shared memory starts in `.claude/project-context/`
- The persistent code documentation wiki lives in `docs/wiki/`
- `docs/wiki/evidence/` is the deterministic raw evidence layer generated by the CLI
- `docs/wiki/pages/` is the durable refinement layer maintained by an LLM or a human
- Repo-local refinement skills live in `.agents/skills/` and `.claude/skills/`
- `docs/wiki/index.md` is the top-level catalog; `docs/wiki/schema.md` and `docs/wiki/refinement-playbook.md` define the maintenance contract
- Treat `.omx/`, `.claude/project-context/`, and `docs/wiki/` as complementary durable context layers

## Wiki-first operating rule

- Treat `docs/wiki/` as the first synthesized knowledge layer for repository questions.
- Before broad code exploration, read `docs/wiki/index.md`, `docs/wiki/schema.md`, and `docs/wiki/refinement-playbook.md`.
- When the request spans multiple modules, workflows, or architectural invariants, run `npm run wiki -- query --query "<terms>"` before searching through `src/` and `tests/`.
- Read `docs/wiki/pages/` as the preferred refined layer, then verify important claims against `docs/wiki/evidence/` and raw files.
- Never hand-edit `docs/wiki/evidence/`; regenerate it with `npm run wiki -- ingest ...` or `npm run wiki -- refresh`.
- Prefer the repo-local skills `wiki-refinement-pass`, `wiki-promote-answer`, and `wiki-refinement-audit` for refinement work when available.
- If a useful answer, comparison, or architectural synthesis emerges during the session, file it into `docs/wiki/pages/`, update `docs/wiki/pages/index.md`, and append to `docs/wiki/log.md`.
- Periodically run `npm run wiki -- lint` to catch broken links, missing coverage, and orphan pages.

## Context navigation rule

1. Consult `.claude/project-context/current-state.md` and `.claude/project-context/architecture.md`.
2. Consult `docs/wiki/index.md`, `docs/wiki/schema.md`, and `docs/wiki/refinement-playbook.md`.
3. Consult `docs/wiki/pages/index.md` and `docs/wiki/evidence/index.md`.
4. For broad or architectural questions, run `npm run wiki -- query --query "<terms>"` before rereading large areas of the codebase.
5. If they exist, consult `graphify-out/graph.json` and `graphify-out/GRAPH_REPORT.md` before rereading large areas of the codebase.
6. Read raw files in `src/` and `tests/` when editing, verifying fine behavior, or when the shared context or wiki looks stale.

## Change guidance

- Preserve the persisted schema of `manifest.json` and `job-state.json`.
- Preserve `--resume` semantics, including `resolvedInputPath`, `inputSizeBytes`, `inputMtimeMs`, `provider`, `transcriberSignature`, and `chunkDurationSeconds`.
- Preserve exit codes: `0` full success, `1` fatal error/invalid usage, `2` reusable partial failure.
- Chunks are always WAV PCM 16-bit mono 16000 Hz before they reach a provider.
- `openai-whisper` stays pinned to `whisper-1`; `openai-transcription` supports backend `openai` or `azure`.
- The build must keep clearing `dist/` before compiling.
- When code structure, workflows, or architectural ownership change materially, regenerate `docs/wiki/evidence/` with `npm run wiki -- ingest ...` or `npm run wiki -- refresh` in the same slice.
- When a task produces durable project knowledge without changing code, prefer filing that analysis into `docs/wiki/pages/` instead of leaving it only in chat history.
- After meaningful wiki maintenance or architecture-heavy changes, run `npm run wiki -- lint`.
